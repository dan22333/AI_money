02

The event router — not everything runs the agent

A fan message deserves a full, thoughtful reply. A payment is mostly a database update (with an optional reaction). A new subscriber is a welcome. So the first thing the brain does is look at the event type and route it to the right handler — this keeps cost down and behavior correct.

EventRouter actionRuns agent?
creator.message.receivedFull agent turn → replyYes — full
creator.payment.succeededRecord purchase, bump spend, link to message_uuid; optionally trigger a thank-youOptional — a short reaction
creator.subscription.activatedCreate/mark fan; optional welcome messageOptional — welcome
creator.subscription.deactivatedMark churned; maybe a win-back laterNo
creator.follow.createdCreate fan recordNo
purchases become conversation A payment arrives on its own webhook, not inside the chat. But it carries message_uuid, so we join it to the exact message/PPV it unlocked, write it into the conversation as a signal, and let Jenny react like a human: "mmm glad you couldn't resist that one 😏". Data and a conversational beat.

05

Media pipeline — human or machine described

Drop a file in a GCS folder and it lands in the Fanvue vault and the catalog. Photos can be auto-described by a vision model; videos (or anything you want precise) can ship with a human-written description — the creator's words win.

The catalog row records metaSource: human|vision and a needsReview flag, plus an admin endpoint to edit later. The heat rating (1–4) maps to the intimacy modes, so Jenny only reaches for EXPLICIT media when she's in EXPLICIT mode. Price can also be pushed to Fanvue via PATCH /media/{uuid}.

The LangGraph agent

One fan message = one run. Four context loads happen in parallel, then Grok decides and acts in a tool loop, then we persist and learn. classify_mode is a real node — the one that picks the intimacy mode, every single turn.

What the model sees each turn

The relationship is infinite, but the context stays small and bounded. Five compact layers are assembled fresh on every message — never the whole raw transcript:

1
PersonaWho Jenny is + the never-break-character directive · from persona.md
2
Fan profilejoined 3w ago · spent $45 · active sub · VIP · from the fans table
3
mem0 facts"night nurse, dog Rex, into tennis" · durable, semantic recall
4
Rolling summaryONE evolving paragraph of all older history · updated as it grows (not a stack)
5
Last ~15 raw messagesthe exact recent flow, verbatim
+
Mode directivefrom classify_mode: "You are in FLIRTY mode — suggestive welcome, not explicit yet"
one summary, not manyWhen history passes a threshold, persist folds the newly-old messages into the single rollingSummary — it never accumulates multiple summary blobs. So "past summaries" are already inside the current one. Cost stays flat whether it's day 1 or day 400.
08

Intimacy modes + live proof

Jenny runs in one of four heat levels, re-decided every turn by classify_mode. The mode gates tone, explicit language, NSFW media, and PPV nudges.

1 · COLDNew / greetings. Welcome, learn name.
2 · WARMFriendly rapport, light flirting. Resting state.
3 · FLIRTYSuggestive, teasing. Teaser media ok.
4 · EXPLICITSexual, explicit allowed. NSFW / PPV in play.

session reset — your ruleA new session always resets to WARM (or COLD if brand new), no matter how steamy last time ended. The summary still remembers it got explicit, so Jenny rekindles naturally — but never cold-opens mid-explicit. Escalation is re-earned each session, exactly like a real person.

10

When & how Jenny sells — one deterministic tool

The agent must never reason over inventory, purchases, or prices — that's where an LLM hallucinates ("here's that video!" — one they already own). So all of it lives in a single deterministic tool, offer_content. The agent only signals "this feels like a sell moment" + a caption in Jenny's voice. The tool does every check and either sells or declines.

AGENT — non-deterministic

Judgment & voice

  • Is this a sell moment?
  • The caption wording
offer_content — deterministic code

Everything financial

  • Unsold & appropriate item?
  • Which item · what price
  • Cooldown / not pushy
  • Send + record it

Inside the tool (all code, zero model judgment)

offer_content(theme, caption):
  1 TIMING    mode>=FLIRTY? monetize_ok? cooldown passed?  → else {status:"not_now"}
  2 ELIGIBLE  catalog WHERE heat<=mode
                     AND uuid NOT IN purchasedUuids      # never re-sell
                     AND uuid NOT IN recentlyOffered
                     AND matches theme                   → if empty {status:"nothing"}
  3 PICK      rank eligible (theme-fit, heat-fit, later: conversion)
  4 PRICE     price = item.suggestedPriceCents
  5 SEND      Fanvue send_media(uuid, caption, price)
  6 RECORD    recentlyOffered+=uuid; lastPpvAt=now; offers++
             → {status:"sent", item, price}
the return contract = your rule sent → the agent's reply rides with it · nothing → keep chatting (flag a content gap) · not_now → keep chatting, try later. A sale never depends on the model remembering inventory. Free teasers use the same pattern via send_teaser (price 0, same dedupe + heat gate) — so the agent hand-picks a mediaUuid or price in no path.
11

Analytics — what actually drives revenue

Yes, the schema is built for this. The whole point of the join key fields is to answer money questions. Because a purchase stores the messageUuid it came from, and each message stores its mode, mediaUuids and sessionId, we can trace revenue back to exactly what caused it.

Questions this answers out of the box

conversion by mode

Does heat sell?

Join purchases → message.mode. "EXPLICIT messages convert at 8%, FLIRTY at 3%."

top content

Which media earns?

purchases → message.mediaUuids → catalog. Best-earning photos/videos & price points.

who pays

Whales & patterns

fans.totalSpend + tier; what mode/media converted each top spender.

timing

Time-to-first-$

firstSeenAt → first purchase ts; which session number tends to convert.

message → buy

What was said

Pull the messages right before a purchase to see the winning lines.

re-engagement

Win-backs

Did a gap + re-engage message lead to a return / purchase?

how it runsFirestore streams to BigQuery (export), where these are plain SQL and Looker Studio dashboards. Firestore serves the live agent fast; BigQuery serves heavy analytics without slowing it down.

Ship pipeline — GitHub → tests → GCP

Nothing reaches production without passing tests. Push to GitHub, GitHub Actions runs the full test suite, and only a green run on main builds the container and deploys to Cloud Run. No manual deploys.

Two workflows

WorkflowTriggerDoes
ci.ymlevery push / PRinstall, ruff lint, pytest (unit + tool + integration + e2e). Blocks merge if red.
deploy.ymlpush to main, after CI greenbuild image → Artifact Registry → deploy Cloud Run (auth via Workload Identity Federation — no keys)

Test pyramid (what we write)

unit

Pure logic

store filters (dedupe purchased, heat gate), cooldown math, session reset, mode-JSON parsing.

tool

Deterministic tools

offer_content: not_now on cooldown, nothing on empty, sent on eligible, never re-sells; send_teaser.

integration

DB & router

Firestore emulator read/write; event router maps each webhook to the right handler; idempotency.

e2e

Agent (mocked LLM)

Full graph with a fake model → verifies wiring, tool calls, sim/real isolation — offline, deterministic.

why a fake LLM in e2eThe model's words are non-deterministic, but the wiring isn't. A scripted fake model lets the whole graph run in CI, offline, proving tools fire and the no-re-sell guarantee holds — every push.

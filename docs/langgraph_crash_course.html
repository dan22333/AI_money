00 — the one idea

It's a graph. State flows through it.

LangChain's older "chains" ran in a straight line. Real agents need to loop ("think → call a tool → think again") and branch ("reply, or send a photo?"). LangGraph models that as a directed graph:

STATE

A shared object

One dict that every step reads and writes. It's the agent's working memory for a single turn — the message list lives here.

NODES

The steps

Plain Python functions. Each takes the state, does one job, returns the fields it wants to change.

EDGES

The wiring

Which node runs next. Fixed edges are straight lines; conditional edges are the decisions (the branches and loops).

You define the graph once, .compile() it, then .invoke() it per message. That's the whole mental model — the rest is detail.

02 — state

State: the dict that flows, and reducers

State is a typed dict. The subtle part is how updates merge. By default a node's return overwrites a field. But the message list must append, not replace — so you annotate it with a reducer, add_messages:

# agent/graph.py
class State(TypedDict):
    messages: Annotated[list, add_messages]  # reducer → appends & de-dupes by id
    fan_id:   str                        # plain → each node overwrites
    incoming: str
why it matters Without the reducer, the agent node returning one new message would erase the whole conversation. With it, each node just returns its new message and LangGraph appends it. Reducers are how parallel/looping nodes safely share one growing list.

A node never mutates state in place — it returns a partial update, and LangGraph applies it through the reducers:

def agent(state: State) -> dict:
    return {"messages": [llm_with_tools.invoke(state["messages"])]}
03 — nodes

Nodes are just functions

No magic. A node is f(state) -> partial_state. Yours each own one responsibility — which is what makes the agent debuggable:

load_context

Recall

Pulls fan facts from mem0 + recent transcript from the DB, then builds the message list: persona → memory → history → new message.

agent

Decide & speak

One LLM call with tools bound. Either emits a reply, or emits tool calls asking to act.

tools

Act

Runs whatever the model asked for — search_vault, send_media, save_fact — and feeds results back.

persist

Save & learn

Writes the turn to the message DB and hands it to mem0 so Jenny remembers next time.

# a node reads state, returns only what it changes
def load_context(state: State) -> dict:
    facts   = memory.recall(state["fan_id"], state["incoming"])
    history = store.recent_messages(state["fan_id"], limit=12)
    system  = SystemMessage(content=PERSONA + "\n\nWHAT YOU REMEMBER:\n" + facts)
    return {"messages": [system, *history_as_messages, HumanMessage(state["incoming"])]}
04 — edges & the loop

Edges: fixed wiring vs. decisions

Fixed edges are unconditional ("after A, always B"). The intelligence lives in conditional edges — a router function reads state and returns the name of the next node:

# fixed edges
g.add_edge(START, "load_context")
g.add_edge("load_context", "agent")
g.add_edge("tools", "agent")      # ← the loop: after acting, think again

# conditional edge = the diamond in the diagram
def route(state) -> str:
    last = state["messages"][-1]
    return "tools" if last.tool_calls else "persist"

g.add_conditional_edges("agent", route, {"tools":"tools", "persist":"persist"})
the ReAct loop agent → tools → agent is the classic reason-act loop. The model calls a tool, sees the result, and gets to think again — possibly calling another tool — until it has nothing left to do and produces a plain reply. That's how "find a photo, then send it, then say something cute" happens in one turn.
05 — tools

Tools: bind them, then let a ToolNode run them

Two pieces. Binding tells the model what it may call (names, args, docstrings become the schema). The prebuilt ToolNode actually executes the calls the model makes:

llm_with_tools = llm.bind_tools([search_vault, send_message, send_media, save_fact])
g.add_node("tools", ToolNode(ALL_TOOLS))   # prebuilt executor

# a tool is a documented function — the docstring IS the model's instructions
@tool
def search_vault(query: str) -> str:
    """Search Jenny's media vault by MEANING to find a photo/video to send."""
    ...
write docstrings for the model The model only knows what a tool does from its name, signature, and docstring. Vague docstring → wrong tool at the wrong time. Treat them as prompt engineering.
06 — memory

Memory: two completely different things

"Memory" gets overloaded. In an agent there are two independent layers, and Jenny uses both:

LayerScopeMechanismIn Jenny
Short-termOne conversation thread The messages list + a checkpointer keyed by thread_id We rebuild it each turn from our own message DB
Long-termEverything you ever learned about a person mem0 — LLM extracts durable facts into a vector store, recalled by meaning memory.recall() / add_fact(), keyed by fan_id

Short-term: checkpointers (thread persistence)

Give compile() a checkpointer and LangGraph saves state after every node, keyed by a thread id. Re-invoke with the same thread and the conversation resumes — survives restarts, enables pause/resume. This is LangGraph's built-in "remember this chat":

from langgraph.checkpoint.postgres import PostgresSaver
graph = g.compile(checkpointer=PostgresSaver(...))
graph.invoke(state, config={"configurable": {"thread_id": fan_id}})
design note for v1 Jenny skips the checkpointer and instead reloads history from our own Firestore message DB in load_context. Same effect, and we own the data for analytics. Add a checkpointer later if you want LangGraph to manage thread state for you.

Long-term: mem0 (the "she remembers me" layer)

mem0 is the semantic memory. It reads turns, extracts facts ("does night shifts", "has a labrador"), de-duplicates them over time, and returns the relevant ones for the current message — so recall stays sharp even after thousands of messages:

memory.add_turn(fan_id, fan_text, jenny_text)   # extract & store facts
facts = memory.recall(fan_id, incoming)          # semantic lookup for THIS msg
07 — summarization

Summarization: keeping context small as chats grow

A months-long chat won't fit in the context window, and stuffing it is slow and expensive. The fix is a summarization node: once the message list crosses a threshold, fold the oldest turns into a running summary and keep only the last few verbatim. It's just another node you drop into the graph before agent:

def summarize_if_long(state) -> dict:
    msgs = state["messages"]
    if len(msgs) <= 16:
        return {}                       # nothing to do
    old, keep = msgs[:-8], msgs[-8:]
    summary = llm.invoke([SystemMessage("Summarize this chat as Jenny's notes."), *old])
    # RemoveMessage tells the add_messages reducer to DROP those ids
    drops = [RemoveMessage(id=m.id) for m in old]
    return {"messages": [*drops, SystemMessage("Earlier: " + summary.content), *keep]}
three altitudes of memory, together Summary compresses this conversation · checkpointer persists this conversation · mem0 remembers the person across all conversations. A convincing "she really knows me" comes from layering all three, not picking one.

Related helper: trim_messages() from langchain-core does token-budget trimming when you'd rather drop than summarize.

08 — why

Why LangGraph here, not a plain loop

branching

Decide, don't script

Reply vs. search vs. send PPV isn't a fixed sequence. Conditional edges let the model drive, with the graph keeping it safe.

persistence

State for free

Checkpointers give durable per-fan threads without you hand-rolling resume logic.

portability

Swap the model

You're on OpenRouter today. The graph doesn't care — change one line to A/B DeepSeek vs. Grok for Jenny's voice.

observability

See every step

Each node is inspectable. When Jenny does something odd, you know whether it was recall, the model, or a tool.

For a one-call-per-message bot none of this earns its weight. Jenny is a decide-then-act agent with memory — exactly the shape LangGraph is for.

09 — glossary

The 60-second glossary

StateGraph — the builder you add nodes and edges to, then .compile().
State — the typed dict passed between nodes; fields merge via reducers.
Reducer — merge rule for a state field (add_messages = append).
Node — a function f(state) → partial update.
Edge — fixed next-node link; conditional edge picks the next node from state.
ToolNode — prebuilt node that executes the model's tool calls.
bind_tools — attaches tool schemas to the model so it can request them.
Checkpointer — saves state per thread_id for resume/persistence (short-term memory).
mem0 — external long-term fact memory, recalled semantically per user.
RemoveMessage — sentinel that tells the reducer to delete messages (used when summarizing).
